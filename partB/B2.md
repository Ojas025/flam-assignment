# B2 — throughput drop in the long-context sweep

Prompt **3584**, gen **512**. Source: `bench_log.csv`.

## The anomaly

| n | wall (s) | reported tok/s | goodput (gen tok/s) | kv_cache_util | preempted_seqs | itl_ms_p50 |
|---|---|---|---|---|---|---|
| 4 | 28.98 | 565.4 | 70.7 | 0.16 | 0 | 51.33 |
| 8 | 36.30 | 902.6 | 112.8 | 0.31 | 0 | 62.26 |
| 16 | 49.97 | 1311.4 | 163.9 | 0.62 | 0 | 77.20 |
| **24** | 61.16 | **1607.4** | **200.9** | 0.93 | 0 | 96.07 |
| 32 | 94.71 | 1384.0 | 173.0 | 0.97 | 7 | 101.79 |
| 48 | 151.41 | 1298.5 | 162.3 | 0.97 | 23 | 100.00 |

- Throughput rises **184%** from n=4 → n=24, then falls **13.9%** at n=32 and **19.2%** at n=48 — even though concurrency rose further.
- Prompt and gen lengths are fixed, so goodput = `n × 512 / wall` = reported / 8. Both metrics reverse.
- Identity `n × 4096 / wall = reported_tok_s` holds within **0.11** on every row.

## Mechanism

1. **Over capacity.** B1 allows ~**25.7** full-length sequences. n=32 / n=48 ask for **1.24×** / **1.87×** the KV budget. Util climbs to **0.93** at n=24 and pins at **0.97** above that.
2. **Evictions.** `preempted_seqs`: 0 → 7 → 23 (matches 32−25 and 48−25). Default mode is recompute: evicted work loses its KV and redoes prefill.
3. **Lost time is not decode.** Decode ≈ `(gen_len − 1) × ITL`:

| n | decode (s) | wall (s) | non-decode (s) |
|---|---|---|---|
| 16 | 39.4 | 49.97 | 10.5 |
| 24 | 49.1 | 61.16 | 12.1 |
| 32 | 52.0 | 94.71 | **42.7** |
| 48 | 51.1 | 151.41 | **100.3** |

- Decode stays ~**50 s**; ITL moves only **6%** from n=24. Non-decode blows up (12.1 → 42.7 → 100.3 s) — waiting and recompute.

4. **Control.** Short-prompt sweep (512+256) reaches n=64 at util **0.47**, zero preemptions, throughput still rising (**2267.3** tok/s). Batch size alone does not cause the drop.
5. **TTFT is weak here.** It rises **+91%** (n=24→48), consistent with queueing, but absolute values look too low (~0.5 s vs ~6–12 s of expected prefill compute). Prefer wall clock, ITL, and KV columns.

## Proposal: fp8 KV (`--kv-cache-dtype fp8`)

```
bytes/token = 57,344 B (56 KiB)
capacity    = 51.4 → 51 sequences (was 25)
util @ n=48 = 0.933
util @ n=32 = 0.622
```

n=48 fits with no preemption.

| | n=32 | n=48 |
|---|---|---|
| preempted_seqs | 7 → 0 | 23 → 0 |
| kv_cache_util | 0.97 → 0.62 | 0.97 → 0.93 |
| reported tok/s, floor | 1384 → ≥1607 (+16%) | 1298 → ≥1607 (+24%) |
| reported tok/s, central | → ~2,291 | → **~2,622** |
| goodput, central | 173.0 → ~286.4 | 162.3 → **~327.8** |
| wall clock, central | 94.71 → ~57.2 s | 151.41 → **~75.0 s** |

- **Floor:** with no preemption, throughput should at least match n=24 (**1607**), unless a new bottleneck appears.
- **Central estimate:** step ≈ (weights + resident KV) / (300 GB/s × 0.66).
  - n=48: resident **11.27 GB** → ~**99 ms**/step → decode ~**51 s** + non-decode ~**24 s** → **~75.0 s**.
  - n=32: resident **7.52 GB** → ~**80 ms**/step → decode ~**41 s** + non-decode ~**16 s** → **~57.2 s**.
- TTFT not predicted (logged values unreliable).

**Risks:** quality impact of fp8 KV; kernel support on L4 unverified; central estimate is fitted to this log, not measured.

**Config-only alternative:** `max_num_seqs=24` removes preemption but queues overflow as a second wave.

- n=48 → 2 × 61.16 = **122 s**, ~**1607** tok/s (+24%)
- n=32 → 61.16 + 36.30 = **97.5 s**, ~**1345** tok/s (−3%) — no gain
- Queued requests wait a full wave (worse TTFT). Useful only near multiples of 24.

## How to confirm

Pull `vllm:num_preemptions_total`: expect 0 for n ≤ 24, ≥7 / ≥23 at n=32 / 48, and 0 after fp8.
