# B3 — misread column in REPORT_v0 §2

## The column

Both §2 claims rest on misreading `reported_tok_s`:

```
reported_tok_s = num_requests × (prompt_len + gen_len) / wall_clock_s
```

That counts prompt tokens as well as output. For user-visible throughput, use generated tokens only: `n × gen_len / wall_clock_s`.

## The two claims

| REPORT_v0 claim | What the log shows |
|---|---|
| “Long prompts give better GPU utilization (1311 vs 883 tok/s at batch 16)” | Long rows count **4096** tokens each vs **768** short. Goodput at batch 16: long **163.9** tok/s; short **294.5** tok/s. Short is **1.8×** better. |
| “Assume ~1600 tok/s per L4… batch 48 → ~3200” | 1600 is batch-24 *reported* (~**201** tok/s real output) — the peak before the KV wall (B2). Batch 48 measured: **1299** reported, **162** goodput. Forecast **3200** is ~**20×** high. |

## What to say instead

- Short prompts beat long on generated throughput: **294 vs 164** tok/s at batch 16.
- One L4 peaks near **200** generated tok/s on ~3.5k-token prompts (batch 24), limited by ~**25** full-length sequences.
- Past batch ~25, throughput falls (preemption / recompute). Do not scale linearly.
- Do not advise packing more context per request — it cuts output rate and burns KV capacity.
